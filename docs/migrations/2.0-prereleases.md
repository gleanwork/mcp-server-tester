# Upgrading from a 2.0 prerelease

This guide covers what changed after `2.0.0-beta.7`. If you're upgrading from 1.x, read [Migrating from v1.x to v2.0](./migration-2.0.md) instead.

From an earlier prerelease, read the [beta.7 migration guide](https://github.com/gleanwork/mcp-server-tester/blob/v2.0.0-beta.7/docs/migrations/migration-2.0.md) first; it covers the changes between prereleases up to beta.7.

These sections of the main guide are also new since beta.7:

- [Custom judges are plugins](./migration-2.0.md#custom-judges-are-plugins)
- [Every judge runs the same way](./migration-2.0.md#every-judge-runs-the-same-way)
- [LLM calls: bearer tokens and streaming](./migration-2.0.md#llm-calls-bearer-tokens-and-streaming)
- [`runVariantExperiment` needs clear evidence to recommend a variant](./migration-2.0.md#runvariantexperiment-needs-clear-evidence-to-recommend-a-variant)
- [Client cases name a client and model, not `mcpHostConfig`](./migration-2.0.md#client-cases-name-a-client-and-model-not-mcphostconfig)
- [Direct cases are Playwright tests](./migration-2.0.md#direct-cases-are-playwright-tests)

## Cowork takes tool variants

**Affects:** manifests that give `cowork` `toolOverrides`, and plugin clients with `runBatch`.

Cowork now gets an arm's `toolOverrides` through MST's tool-variant proxy, so a tool optimization (`runVariantExperiment` on a suite) can run on Cowork. Before, validation rejected it. ChatGPT still opts out.

For plugin clients:

- `serversPerBatch: true` says the client connects to one server set for the whole batch, the first request's `input.servers`. The batch then shares one proxy endpoint, and the check that the client listed the variant's tools is for the batch.
- A proxied request carries `input.checkServers`, the same servers on an endpoint for the client's own checks (a readiness probe, say), so that traffic isn't taken for the model seeing the variant.

## Cowork and ChatGPT options aren't nested

**Affects:** manifests that use `cowork` or `chatgpt` with `clientOptions.options`.

Their options go directly in `clientOptions`, like every other client's. A nested `options` object fails with a message saying so.

```json
// Before
{ "client": "cowork", "clientOptions": { "options": { "appVersion": "1.52386.6" } } }

// Now
{ "client": "cowork", "clientOptions": { "appVersion": "1.52386.6" } }
```

## The client, its model and its options are separate keys

**Affects:** every manifest, arm and case that sets `host`, and shared configs (`configs` in a plugin).

`host` is now three keys: `client` names the client under test, `model` the model it uses, and `clientOptions` the client's other options. A config that still sets `host` fails with a message naming them.

```json
// Before
{ "host": { "type": "cowork", "model": "claude-sonnet-4-6", "timeout": 900000 } }

// Now
{ "client": "cowork", "model": "claude-sonnet-4-6", "clientOptions": { "timeout": 900000 } }
```

- **Arms and cases** take the same three keys. An arm that sets only `model` keeps the manifest's client and options; one that sets a different `client` doesn't inherit the manifest's `clientOptions`.
- **The manifest's `model`** is a default for every arm and case, as before.
- **`clientOptions` can't set `type`, `client` or `model`;** each has its own key.
- **Shared configs.** A manifest that sets `client` or `clientOptions` replaces a shared config's client, so one client's options never apply to another.
- **Results.** A validated manifest (`validateManifest`) holds each level's resolved client in the same three keys. Result fields are unchanged in this release.

## Tool optimization reports a comparison

**Affects:** code that reads `runVariantExperiment` results or the reporter's `mcp-variant-experiment` attachment.

With `testInfo`, `runVariantExperiment` also attaches a case-by-case comparison, and the reporter opens on a **Comparison** tab. Each candidate gains `measurement` and `improvement`, whose paired changes carry an `assessment` of `'better'`, `'worse'` or `'unclear'`. Case groups are capability and regression cases (`measurement.capability`, `measurement.regression`). The result says where the groups came from in `grouping` (`'declared'` from the `regression` tag, or `'grouping-run'`, with the extra run in `groupingBaseline`). On a suite, an arm metric such as `input_tokens_mean` has no per-case scores, so its improvement isn't tested; a variant that improves it is recommended unless it breaks regression cases.

## Clients have canonical names

**Affects:** manifests and datasets that name a built-in host, plugins that contribute hosts, `HostDefinition` and the other `Host*` types, and imports from `./experimental/hosts`.

What an eval tests is an MCP client with a model ([ADR 0002](../adr/0002-common-eval-vocabulary.md)). Built-in clients have canonical names, and how MST drives one isn't part of its name. An old name fails with a message naming its replacement, for example `Client "claude-cli" is now "claude-code".`; the 2.0 deprecated aliases (`cowork_cu` and the long driver names) fail the same way.

| Before                         | Now                                       |
| ------------------------------ | ----------------------------------------- |
| `vercel-sdk`, `anthropic-api`  | `mst`                                     |
| `claude-cli`                   | `claude-code`                             |
| `chatgpt-mac`, `chatgpt-linux` | `chatgpt` (the platform picks the driver) |
| `cowork`                       | `cowork`                                  |

`anthropic-api` was a second implementation of what `mst` does, so it's removed. `mst` infers the API from the model id (`claude-*`, `gpt-*`, `gemini-*`, `claude-*@date` for Vertex); set `provider` to override it.

For plugins and TypeScript:

- A plugin contributes clients under `clients` (was `hosts`), and a plugin with `hosts` fails validation naming `clients`.
- Types: `HostDefinition` → `ClientDefinition`, `HostRunInput` / `HostRunContext` / `HostRunResult` / `HostRunOptions` / `HostBatchRequest` → `ClientRun*` / `ClientBatchRequest`, `HostConfig` → `ClientConfig`, `HostEvent` → `TraceEvent`, `HostEvidence` → `TraceEvidence`, `HostTrace` → `Trace`, `HostPlugin` → `MarketplacePlugin`.
- `@gleanwork/mcp-server-tester/experimental/hosts` is now `/experimental/clients`.

The config key is `client`; see [The client, its model and its options are separate keys](#the-client-its-model-and-its-options-are-separate-keys).

## Cases and run controls use common eval terms

**Affects:** every dataset and manifest, `runEvalDataset` and `runVariantExperiment` options, CLI host args, and plugin hosts.

MST now uses the vocabulary other eval frameworks share ([ADR 0002](../adr/0002-common-eval-vocabulary.md)). Old keys fail validation with a message naming the replacement, for example ``case "a" iterations: `iterations` is now `trials` ``; none of them is an alias.

| Before                                             | Now                                      | Where                                               |
| -------------------------------------------------- | ---------------------------------------- | --------------------------------------------------- |
| `scenario`                                         | `input`                                  | case                                                |
| `iterations`                                       | `trials`                                 | case, manifest, `run`                               |
| `accuracyThreshold`                                | `passThreshold`                          | case, manifest, `run`                               |
| `expect`                                           | `assertions`                             | case                                                |
| `canonicalAnswer`                                  | `expected.answer`                        | case                                                |
| `scenarioTemplate` with `{{scenario}}`             | `inputTemplate` with `{{input}}`         | manifest, arm                                       |
| `{{scenario}}`                                     | `{{prompt}}`                             | CLI host `args` (`mcpHostConfig.cli.args`)          |
| `defaultLlmIterations`, `defaultAccuracyThreshold` | `defaultTrials`, `defaultPassThreshold`  | `runEvalDataset` and `runVariantExperiment` options |
| `EvalExpectBlock`, `EvalExpectBlockSchema`         | `EvalAssertions`, `EvalAssertionsSchema` | types                                               |

Plugin hosts receive the case's input as `input.prompt` (was `input.scenario`). A batch request numbers its trial as `request.trial` (was `request.iteration`). Judges are unchanged: they already read `case.input.prompt` and `case.expected.answer`.

A manifest that used a renamed key has a new `contentHash` once it's updated, so `runEvalBatch` doesn't resume a run saved before the change. Result fields (`iterations`, `assertionPassRate` and the request's `scenario` and `expect`) are unchanged in this release.

## Cowork runs the installed Claude Desktop unless the manifest pins one

**Affects:** macOS Cowork runs, and anyone who set `MST_COWORK_APP_VERSION`.

MST no longer downloads a built-in Claude Desktop version (1.52386.6) for each run. It runs the installed `/Applications/Claude.app` and records its version with every case result as `hostTelemetry.hostApp` (`{ name, version, source }`). To run an exact version, set `host.options.appVersion` in the manifest; MST downloads and verifies it as before, and records `source: 'pinned'`. `MST_COWORK_APP_VERSION` now fails with a message pointing to `appVersion`. `coworkSetup.approveWriteTools` no longer requires 1.52386.6. Suite results also record MST's own `packageVersion`. See [Which Claude Desktop runs](../cowork.md#which-claude-desktop-runs).

## The Claude CLI host runs isolated from your Claude Code setup

**Affects:** `claude-cli` hosts.

The host used your own Claude Code configuration, so your skills, plugins and settings shaped what the model did, and added to its input tokens. It now gives each run an empty `CLAUDE_CONFIG_DIR`, so your `settings.json` (its `env` block, `apiKeyHelper`) doesn't apply either. Authenticate through the environment (`provider: 'vertex'`, or an Anthropic API key), or set `isolate: false` on the host to use your own configuration, for example to sign in with a claude.ai account. See [Claude Code isolation](../mcp-host.md#claude-code-isolation).

## Variant experiments run on suites

**Affects:** `runVariantExperiment` result types (see below); otherwise new.

`runVariantExperiment({ suite: { manifestPath }, variants })` runs tool variants as arms of a manifest, so experiments reach any host that takes tool variants, not only the SDK host, and can optimize any numeric arm metric (`better: 'lower'` for tokens or cost). The dataset form, `runVariantExperiment(options, context)`, runs as before, except that `metric` on its results is typed as a string (any arm metric) rather than `ExperimentMetric`, and a candidate with no value for the metric is disqualified (`metricUnavailable: true`) instead of scoring as the baseline. `runEvalSuite` gains `arms`, which replaces the manifest's arms with a list or with a function of them.

## Internals leave the root

**Affects:** code that imports `BUILTIN_RESULT_SCHEMAS`, `getResponseSizeBytes`, `SKILL_LIMITS` or `skillDigest` from `@gleanwork/mcp-server-tester`.

These were internals:

- `BUILTIN_RESULT_SCHEMAS` is the expectation engine's table for named `schema` expectations.
- `getResponseSizeBytes` is how `validateSize` measures a response; check a size with `validateSize` or `toHaveToolResponseSize`.
- `SKILL_LIMITS` and `skillDigest` are the skills client's size limits and digest; `mcp.skills` and the skills conformance checks apply them.

## Desktop hosts have one naming style

**Affects:** manifests whose host is `chatgpt`, `cowork_cu`, `openai.chatgpt.agent.desktop-app.macos`, `openai.chatgpt.agent.desktop-app.linux` or `anthropic.claude.cowork.desktop-app.macos`.

Built-in host names are kebab-case: `vercel-sdk`, `anthropic-api`, `claude-cli`, `cowork`, `chatgpt-mac` and `chatgpt-linux`. The earlier names still work and print a deprecation warning (`MST_DEPRECATED_HOST`) naming the replacement:

| Earlier name                                | Use                              |
| ------------------------------------------- | -------------------------------- |
| `cowork_cu`                                 | `cowork`                         |
| `anthropic.claude.cowork.desktop-app.macos` | `cowork`                         |
| `openai.chatgpt.agent.desktop-app.macos`    | `chatgpt-mac`                    |
| `openai.chatgpt.agent.desktop-app.linux`    | `chatgpt-linux`                  |
| `chatgpt` (the host for the local platform) | `chatgpt-mac` or `chatgpt-linux` |

The long names remain the external-host driver identities recorded in results; only the host `type` changes.

## The Claude Agent SDK is an optional peer dependency

**Affects:** the `anthropic-agent-sdk` judge provider.

`@anthropic-ai/claude-agent-sdk` (about 46 MB) was a dependency, installed with MST whether or not a judge used it. It is now an optional peer dependency, loaded only when an `anthropic-agent-sdk` judge runs. If you use that provider, install it:

```bash
npm install --save-dev @anthropic-ai/claude-agent-sdk
```

Without it, the judge fails with an error that names the package. The other judge providers already worked this way.

## Plugins are objects

**Affects:** every plugin; code that calls `registerJudge` or the `register*`, `get*`, `list*` and `clear*` registry functions; `METRIC_REGISTRY`; `loadPlugins`; and manifests and datasets that reference plugin extensions.

Plugins now use ESLint's model ([Plugins](../evaluation-framework.md#plugins), [ADR-0001](../adr/0001-eslint-style-declarative-plugins.md)). A plugin is a plain object that MST reads, instead of a module whose hook calls MST's register functions.

```typescript
// Before (2.0.0-beta.7)
import { registerJudge } from '@gleanwork/mcp-server-tester';
import { registerDatasetSource } from '@gleanwork/mcp-server-tester/evals';

export function register() {
  registerJudge({ name: 'completeness', schema, evaluate });
  registerDatasetSource({ name: 'legacy', schema, load });
}

// After
import type { Plugin } from '@gleanwork/mcp-server-tester';

export default {
  meta: { name: '@acme/mst-plugin', version: '1.0.0', namespace: 'acme' },
  judges: { completeness: { schema, evaluate } },
  datasetSources: { legacy: { schema, load } },
} satisfies Plugin;
```

- **Default-export a plugin object.** The loader no longer calls `register`, `registerPlugins`, `registerGleanJudges` or a default-exported function. A module that still exports one fails with a message pointing here.
- **Extension definitions lose `name`.** The map key is the name.
- **Reference plugin extensions as `namespace/name`:** `{ "type": "acme/legacy" }` in manifests, and `{ "judge": "acme/completeness" }` in datasets and `toPassToolJudge`. Bare names belong to built-ins, so a plugin can no longer register a bare `correctness` or replace `file`.
- **A manifest must load the plugins it references.** Referencing `acme/...` without `acme` in that manifest's `plugins` (or `--plugins`, or the `plugins` option) is an error, even if another manifest in the same batch loaded it.
- **`--plugins` and the `pluginPaths` option add to the manifest's `plugins`** instead of replacing them.
- **Manifest plugin paths resolve relative to the manifest's directory,** then `rootDir` (`--root-dir`, the working directory by default), then as package names, resolved as `import` resolves them (exports conditions, including `module-sync`, and subpath patterns), so a package subpath must be a file or an `exports` entry. Before, they resolved against `rootDir` only.
- **Plugins are validated when they load.** Unknown top-level keys are rejected, every extension needs a Zod `schema` and its kind's function (`load`, `run`/`runBatch`/`createConfig`, `evaluate`, `compute`, or `create`), and a different plugin claiming a loaded namespace throws. An old `registerJudge(name, executor)` judge becomes `{ schema: z.object({}).passthrough(), evaluate: executor }`.
- **Datasets are checked too.** A case's `client` and `passesJudge.judge` must name a built-in or a namespace the suite loads.
- **Plugins can share manifest settings.** `configs` holds named manifest fragments (`PluginConfig`) that a manifest applies with `"extends": ["namespace/name"]`. See [Plugins](../evaluation-framework.md#plugins).
- **`getBuiltinHostConfig` resolves built-in hosts only.**
- **`validateManifestRegistrations` is now `validateManifest`** (from `./evals`).
- **Code passes plugin objects** where it used to call register functions: `runEvalSuite({ ..., plugins })`, `runEvalBatch({ ..., plugins })`, `runEvalDataset({ dataset, plugins }, ctx)`, `runEvalCase(evalCase, ctx, { plugins })`, or `test.use({ mcpPlugins: [plugin] })` in Playwright. Code that calls `validateJudge` or the matchers outside those uses `installPlugins([plugin])`, from the package root. For a one-off judge, wrap it in a small local plugin, such as `{ meta: { name: 'local', namespace: 'local' }, judges: { x } }`.
- **Removed:**
  - From the root: `registerJudge` (both forms) and the `CustomJudgeExecutor` and `CustomJudgeResult` types. A plugin judge's `evaluate` takes the same arguments as the old executor; it also needs a `schema`.
  - From `./evals`: `registerDatasetSource`, `registerHost`, `registerMetric`, `registerResultStore`, and their `get*`, `list*` and `clear*` counterparts; `METRIC_REGISTRY`; and `loadPlugins`, `loadPluginModule`, `EvalPluginModule` and `LoadPluginsOptions`.
  - The metric-record argument of `resolveMetric` and `computeMetrics`. Metrics resolve from built-ins and loaded plugins only, and `BUILT_IN_METRICS` is read-only.
- **The `glean-legacy` dataset source example was removed.** It encoded one organization's legacy dataset schema and judge policy, which belongs in that organization's plugin, not in MST. Copy it from the `v2.0.0-beta.7` tag (`examples/plugins/legacy-glean-datasets.ts`) if you need it, and convert it to a plugin object as above. [Dataset sources](../evaluation-framework.md#dataset-sources) shows a dataset-source plugin.

## A judge's schema sees only its own options

**Affects:** plugin judges whose schema reads `type`, `name`, `threshold`, `reference` or `reps`, mainly judges listed in a manifest's `judges`.

A manifest judge's schema used to receive the whole manifest entry, so its options included `type`, `reference` and the case's settings. It now gets only its own options on every path. Read the reference from `case.expected.answer` in `evaluate`'s input. A dataset's `passesJudge` now also passes `provider`, `model` and the other LLM fields to a named judge's schema; beta.7 dropped them. A custom-text rubric's metrics key is now `rubric`, not `judge`. Two manifest judges of the same type (two `rubric` judges, say) stay separate, and a case entry overrides the one whose results carry the same name. The built-in `rubric` judge can also be listed: `judges: [{ "type": "rubric", "rubric": "correctness" }]`.

## A judge's evaluate takes `({ case, trial }, options)`

**Affects:** every plugin judge.

```ts
// Before
evaluate: async (candidate, reference, options) => grade(candidate, reference);
// After
evaluate: async ({ case: c, trial }, options) =>
  grade(trial.response, c.expected.answer);
```

`candidate` is `trial.response` (its text is `trial.text`) and `reference` is `case.expected.answer`. The input also has the case's prompt or tool call, `expected.criteria`, tags and metadata, and the run's tool events, messages and evidence. A judge may declare `requires` paths, and may return `pass`, `skipped`, `subScores`, `usage` and `metadata`. A dataset case may set `expected` (`answer`, `criteria`, other keys); `expected.answer` overrides `canonicalAnswer`. A score outside 0 to 1 is now an error. See [Judge contract](../evaluation-framework.md#judge-contract).

## Hosts take a system prompt

**Affects:** manifests that compare instructions, such as an organisation's, across arms.

`vercel-sdk`, `anthropic-api` and `claude-cli` accept `systemPrompt`, as does `mcpHostConfig.systemPrompt` (a CLI host through a `{{systemPrompt}}` placeholder in `cli.args`); see [System prompts](../evaluation-framework.md#system-prompts). `anthropic-api` used to reject it as an unknown option. Hosts that can't apply one still reject it, and a suite rejects a case prompt that would replace the arm's.

## Claude Code host tools are typed events

**Affects:** expectations and metrics on Claude CLI or Cowork runs that name `Skill`, `SlashCommand`, `Task`, `Agent` or `ToolSearch` as tool calls; plugin hosts that report tool searches.

The Claude CLI and Cowork parsers used to record these as host tool calls. They are now typed events: `Skill` is a `skill` event named for the skill, `SlashCommand` a `command`, `Task` and `Agent` a `subagent`, and `ToolSearch` a new `tool_search` event with the tools it returned in `results`. See [Claude Code host-native events](../evaluation-framework.md#claude-code-host-native-events).

- **Expectations:** match a skill with `{ "name": "triage", "kind": "skill" }`, not `{ "name": "Skill" }`. `toolsTriggered` calls accept `kind: "tool_search"`.
- **Counts:** these events are no longer tool calls, so they leave `tool_count`, `first_tool`, `is_no_action` (a trial that only searched or loaded a skill is now no action), the `toolCallCount` expectation and run telemetry's `toolCalls`. They still count in `host_event_count`. Every arm reports the new `tool_search_hit_rate` when its host searched.
- **Plugin hosts** that search a tool catalog should report `{ kind: 'tool_search', source: 'host', name, results }`.

## Tool variants reach plugin hosts and the Claude CLI

**Affects:** plugin hosts with `run` or `runBatch`, and manifests that give `claude-cli` or such a host `toolOverrides`.

These hosts used to fail validation with `toolOverrides`. Now the suite serves them the arm's servers through a local MCP proxy that applies the variant: each host request gets `http` configs for its own loopback Streamable HTTP endpoints, one per server, with the same labels, so the host must speak Streamable HTTP. See [Tool variants on every host](../evaluation-framework.md#tool-variants-on-every-host).

- **A host request that never lists the proxied tools fails**, with an error naming the variant.
- **Proxied hosts don't see the variant in `context`:** the proxy applies it. A host that applies variants itself must declare `toolOverrides: true`, as before.
- **`HostDefinition.toolSurfaceProxy: false`** opts a host out, for one that connects to servers other than `input.servers`; giving it `toolOverrides` stays a validation error. The Cowork and ChatGPT desktop hosts opt out until they are verified with the proxy.

## Tool variants: one rule, and renames

**Affects:** `toolOverrides` passed to `runEvalDataset()`, and error messages matched in tests.

Every host applies a tool variant through one tool surface, so a variant means the same thing on every host:

- **Keys:** a tool's name on its server, or `server.tool` to pick one of several servers in a suite; a qualified key wins over a bare one. `runEvalDataset()` serves one unlabelled server, so it takes bare names, as before.
- **Renames:** an override can set `name`. Calls to the new name reach the original tool, and are recorded under the original name, so a dataset's expectations need no change between arms. The trace's `rawName` keeps the name the model used.
- **Errors:** an unknown key is `toolOverrides variant "v" overrides unknown tool "x".`, an ambiguous one `... matches a tool on several servers; use "server.tool".` (was `references unknown tool(s)` / `Unknown tool override` / `Ambiguous tool override`). A rename that isn't a valid tool name, or takes a name another tool on the same server has (originally or by rename), is an error.

Plugin hosts that declare `toolOverrides: true` can apply variants with `buildToolSurface()` from `./evals`, and should record a renamed tool's calls under its original name (`resolve()` gives it) with the model's name in `rawName`.

## Comparison orchestrators are arms

**Affects:** code that calls `runServerComparison()`, `saveServerComparison()` or `runSkillsComparison()`, or stores or reads `server-comparison` artifacts.

All three are removed, along with their types and the `server-comparison` result-store kind:

- **Server comparisons:** run two suite arms with different `servers`. Arms run one after another, and per-case wins come from `compareEvalRuns()` on the two arms' results. See [Server comparisons are suite arms](./migration-2.0.md#server-comparisons-are-suite-arms).
- **Skills comparisons:** run arms that differ in the `vercel-sdk` host's new `skills` option (`off`, `catalog`, `preload`), with `metrics: ["skill_loaded", "skill_before_tool", "skill_verification_failed"]`. A case can't also set `mcpHostConfig.skills`: the suite rejects it, since the case setting would override every arm's. See [Measuring whether skills help](../skills.md#measuring-whether-skills-help).

`runVariantExperiment()`, which proposes and scores tool-description variants over rounds, stays.

## Arms report every metric

**Affects:** code that reads arm `metrics`, `armDeltas` or `unavailableMetrics`.

- **More metrics per arm.** Every arm now reports tool counts, MCP calls and host events, tokens, cost, duration and judge results when the host or cases report them, whatever the manifest lists. `mcp_call_count` and `host_event_count` are new metrics.
- **Unavailable metrics.** `unavailableMetrics` lists only metrics the manifest lists.
- **Deltas.** `armDeltas` gain `metricDeltas`: the change in every numeric metric, keyed like `metrics`.
- **Pricing.** A manifest's `pricing` (USD per million tokens, by model) estimates cost for hosts that report tokens but not cost. Estimates are `estimatedCostUsd` in usage, kept apart from `totalCostUsd`; arms report their `costSource`, the prices they used, and `unpricedModels`. See [Pricing](../evaluation-framework.md#pricing).
- **Shared configs** can also set `pricing`, `accuracyThreshold`, `temperature` and `maxTokens`.

## Manifest paths are relative to the manifest

**Affects:** suites run from another directory than their manifest's, and `file` result stores with a relative `dir`.

- **Datasets.** Dataset paths resolve against the manifest's directory first, then `rootDir` (`--root-dir`, the working directory by default), as plugin paths already did; they used to resolve against `rootDir` only. If both directories have the file, the one next to the manifest now wins.
- **Stores.** A `file` store's relative `dir` is relative to the manifest. It used to be relative to the process's working directory.
- **Dataset sources** get `manifestDir` in their context.
- **Comparison with the previous run.** Each run summary has a `runId` and, when the manifest ran the same arms before, a `previousRun` comparing the two, arm by arm. With a result store, the previous run is the newest summary of the same manifest, not the store's `latest` (which any manifest may have written). See [Compared with the previous run](../evaluation-framework.md#compared-with-the-previous-run).

## Settings a run would ignore are errors

**Affects:**

- manifests and datasets with keys MST doesn't define
- manifests with `toolOverrides` or a `concurrency` the host can't honour
- `anthropic-api` hosts with options it doesn't use
- `claude-cli` arms whose servers set connection policy
- arms or cases that switch host type
- manifest-level `temperature`, `maxTokens` or `provider`

The changes:

- **Manifests are strict.** An unknown top-level key is an error; it used to be ignored.
  - **Newly declared:** `accuracyThreshold`, `filterTags`, `run`, `temperature`, `maxTokens`, `redactStoredResponses` and `$schema` were read or allowed without being declared, and are now part of the schema.
  - **`accuracyThreshold`:** a default for host cases that don't set their own, at the top level or as `run.accuracyThreshold`.
  - **Editor schema:** `schema/eval-manifest.schema.json` now declares every key, including `extends` and `coworkSetup`, and rejects the rest.
- **Datasets are strict.** An unknown key in a dataset, a case, or an `expect` block (including inside `responseSize`, `toolsTriggered` calls and `toolCallCount`) is an error, and so is an unknown option on a rubric judge.
  - **Examples:** `regex` (the key is `matchesPattern`), `judge` (it's `passesJudge`), or a misspelt `accuracyThreshold`. These used to be silently dropped.
  - **Named judges are the exception:** a judge named by `judge` still gets its own options.
  - **Errors** name the dataset and case, and suggest the right key for common mistakes.
- **Hosts declare what they honour.** `HostDefinition` gains `toolOverrides` (it shows the model an arm's tool variants) and `maxConcurrency`.
  - **Tool variants:** `toolOverrides` for a host without the flag is a validation error. MST's `vercel-sdk` and `anthropic-api` set it, as does any host with only `createConfig`, because MST's SDK host runs it. Cowork and plugin hosts used to run with the original tools while results recorded the variant; `claude-cli` and ChatGPT used to fail only once a case ran. A plugin host that applies variants itself, from `context.arm`, sets `toolOverrides: true`.
  - **Concurrency:** ChatGPT declares `maxConcurrency: 1`.
- **Defaults reach only the hosts that take them.** A manifest's `model`, `provider`, `maxToolCalls`, `timeout`, `temperature` or `maxTokens` fills in each host option its schema declares. A shared `provider` no longer reaches `anthropic-api`, which has none. A default that none of the run's hosts takes is an error.
- **A host inherits options only from the same host.** An arm, or a case, that switches host type no longer gets the other host's options.
- **`anthropic-api` options are strict.** It used to accept and ignore options such as `systemPrompt` or `provider`.
- **Checks run before anything does, including in `--dry-run`.**
  - **Before execution:** `claude-cli` connection settings it can't forward (OAuth, client credentials, TLS, proxies, retries, timeouts), case-level hosts, and host concurrency are all checked first.
  - **Dry runs:** a dry run now loads datasets, without resolving hosts or secrets.

## Suite metrics are per trial

**Affects:** suites with `iterations` above 1, code that reads `cost_usd`, `first_tool` or per-case metric values, code that reads arm summaries, and code that builds a `MetricResult`.

- **Per-trial means.** Arm metrics used to read the last iteration's trace and every iteration's summed usage, so with 10 iterations `tool_count_mean` counted one trial and `input_tokens_mean` was ten times a trial's. Usage, timing, tool and answer metrics are now means over each case's trials.
- **No infrastructure failures.** Runs that failed on infrastructure aren't trials, including a single run.
- **Shares.** `response_success` and `is_no_action` are shares of trials, so their per-case values are numbers, not booleans; their `_rate` keys are unchanged.
- **`first_tool`** names MCP tools `server.tool`, as multi-server arms already did.
- **New per-arm fields.** Every arm now reports `passed_rate` and `trial_pass_rate` (the share of passing trials), and `armDeltas` add `trialPassRate` and `trialPassRateDelta`. Arms also report `evidence` (the weakest among their cases) and `unavailableMetrics`, and `MetricResult` has `unavailable`.
- **Cost.** Hosts that don't know their cost no longer report 0: the Vercel AI SDK and `anthropic-api` hosts, and CLI or Claude traces without a cost. `cost_usd` is unavailable for them rather than zero.

See [Metrics](../evaluation-framework.md#metrics).

## External-host capabilities are built in

**Affects:** code that calls `registerExternalHostCapability`, datasets whose `externalHost.capabilities` bind `uses: "module:<specifier>#<export>"`, and code that imports `ExternalHostCapabilityImplementation` or `ExternalHostCapabilityContext`.

The desktop drivers' capabilities are no longer an extension point. `registerExternalHostCapability`, `ExternalHostCapabilityImplementation` and `ExternalHostCapabilityContext` are removed from `@gleanwork/mcp-server-tester/experimental/hosts`, and `uses` no longer accepts `module:` ids. A binding can still choose among the built-in implementations (`uses: "builtin:..."`). A `module:` binding fails the case as an unsupported host, with an error that says `module:` capabilities were removed and points to [Hosts](../evaluation-framework.md#clients).

To run a host MST doesn't ship, provide it from a plugin's `hosts` and select it in a manifest. See [Hosts](../evaluation-framework.md#clients).

## The Computer Use planner uses MST's LLM gateway settings

**Affects:** Cowork and macOS ChatGPT runs with `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` or `MST_LLM_AUTH_COMMAND` set, and Cowork on Macs whose managed preferences set the inference provider.

The Computer Use planner resolves its endpoint with the rules in [LLM gateways](../llm-gateways.md#which-credential-is-used). With `ANTHROPIC_BASE_URL` set, it sends the `MST_LLM_AUTH_COMMAND` token or `ANTHROPIC_AUTH_TOKEN` to that URL as a bearer token, or else `ANTHROPIC_API_KEY`. Without it, the planner calls the public Anthropic API with `ANTHROPIC_API_KEY`, and a gateway token is never sent there. In `2.0.0-beta.7` the Python SDK read these variables itself and could mix them; `2.0.0-beta.8` ignored them and always called the public API. If you export `ANTHROPIC_BASE_URL` for something else and want the planner on the public API, unset it for the run.

Cowork no longer requires `ANTHROPIC_API_KEY` when managed preferences set `inferenceProvider`: Claude Desktop takes inference from them, so MST stages no inference credential. Managed preferences may also set `deploymentDisplayName`. See [Cowork inference](../cowork.md#inference).
